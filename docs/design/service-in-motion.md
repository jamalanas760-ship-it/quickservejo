# Service in Motion

QuickServe's launch screen uses two opening curtains, a full-width top video window, centered editorial text and a bottom-aligned QuickServe status across mobile, tablet and desktop and rounded cutouts of a short local restaurant video. GSAP and masked SplitText reveal the words; a single CSS transform reveals the footage. A single 3.33-second H.264 video combines two Pexels clips (102 KiB, no audio) to avoid decoding multiple streams. The current application remains React; Webflow, scrolling libraries and scroll triggers are not needed for this short standalone loading screen.

No third-party request, account or paid service is needed at runtime. A small inline boot script starts the local video and CSS opening immediately before React hydrates. The boot immediately assigns the local clip to the media element for native playback. A background fetch optionally prepares a seekable in-memory URL for the hydrated primary overlay. Neither the boot nor the primary overlay waits for that fetch: the primary uses the prepared URL if ready, otherwise it starts native loading immediately. This prevents a slow or stalled fetch from leaving the entire loading screen on its poster. The primary resumes the saved playhead and elapsed time. The boot player is stopped on handoff and the temporary URL is released after use. The local poster is used for reduced motion, Save Data, blocked autoplay or video failure. Video plays muted and inline once at 0.8× speed, pauses when hidden and is released on unmount. The entry waits at least 4.7 seconds, then closes once the router is ready and video playback has ended or is unavailable; at 5.6 seconds it yields to the page’s own loading or error controls. Recovery is exposed by 6.2 seconds if a pending screen remains. The full-document startup appears once per document; each later route-loading screen plays its own video and effects once. A pending view already hidden by the primary entry does not restart that same launch. Scrolling is locked only while a launch view is visible, with a timed boot unlock for recovery if hydration fails. Reduced-motion settings disable text, panel and indicator animations. Navigation updates that leave motion enabled do not restart or interrupt the sequence.

## Verification

When device reduced motion, Save Data or workspace navigation settings suppress the loader, an “Enable loading animation” button provides an explicit loader-only choice. It reloads the current URL with `loadingAnimation=on`, preserving other parameters. Boot applies this choice before playback and remembers it in local storage. The same override governs both video/GSAP and CSS effects, so they cannot disagree. `loadingAnimation=auto` clears the choice and restores automatic preferences. No system or workspace setting is modified. Storage restrictions still allow the query choice for the current visit.

Check mobile, desktop and landscape layout; actual video time progression; reduced motion and Save Data; video error and autoplay rejection; visibility pause/resume; launch recovery; and an indefinitely delayed optional boot fetch while native media playback remains available. Browser autoplay and decoding depend on device settings; the poster remains if playback cannot start. Test results do not guarantee performance on all phones.
